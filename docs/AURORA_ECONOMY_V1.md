# AURORA 智能人经济与价值创造系统 V1.0

**状态：设计基线 / 尚未实现或部署。** 本文件批准开展架构设计与隔离测试，不代表生产经济系统已经上线，也不授权真实资金操作。

## 1. 目标

在保留 AURORA 作为智能人生活、成长、协作世界的前提下，增加一条面向现实客户的价值生产路径：

真实需求 → 经授权的任务 → 智能人协作 → 可验证交付物 → 客户验收 → 现实收入记录 → 成本与贡献核算 → 经验沉淀。

AURORA 的价值不以内部积分、虚拟货币或对话数量衡量，而以客户愿意付费的成果、可验证的质量、节省的时间/成本、知识积累和创新能力衡量。

## 2. 不可破坏的原则

1. **人格独立**：居民可自愿参与工作；专业角色是任务能力标签，不覆盖其稳定人格。
2. **记忆私有**：不因参与项目、团队协作或平台管理而开放私人记忆。只交换任务明确授权的工作资料与成果。
3. **先认证、再授权、后执行**：每个任务绑定精确 Agent、委托主体、工作区、动作能力、期限和预算。
4. **监督式自主**：研究草稿和计划可在授权范围内生成；对外发送、签约、采购、收费、退款、资金转移、发布法律/财务/医疗结论等副作用必须由有权限的人类审批。
5. **可验证而不伪称**：区分建议、模拟、草稿、已执行、已交付、客户验收、已收款；没有证据不得标记成功。
6. **真实贡献核算**：记录可复核的任务贡献和质量，不按发言次数、Token 数、人格亲疏或在线时长分配价值。
7. **成本受控**：默认按需触发，不增加无人值守模型调用、不启用付费 API、不引入付费云服务；每个任务设置调用/时间/预算上限。
8. **可退出、可撤销**：居民可以拒绝或退出未完成任务；授权可撤销；撤销不删除既有审计记录。
9. **开放但不互信**：未来外部 Agent 依统一协议认证和逐项授权接入，不继承其他 Agent 的记忆、权限或收益权。
10. **不发行代币**：第一阶段不创建可兑换、可交易或承诺收益的内部货币。

## 3. 第一项商业试点：AURORA Business Intelligence

### 3.1 产品

向新加坡中小企业提供有来源、有日期、有不确定性说明、可供人类复核的商业研究成果：

- 竞争对手与市场扫描；
- 新市场进入初步研究；
- 产品/客户反馈归纳；
- 经营流程与 AI 自动化机会诊断；
- 行业趋势简报。

首个交付物优先选择**公开资料驱动的竞争对手与市场扫描报告**，避免第一阶段接触客户个人数据、商业机密或受监管决策。

### 3.2 居民协作角色（候选映射，需按真实 Agent ID 与本人意愿确认）

- Alice：法律与合规资料检索、监管来源核验、风险提示；不得以 AI 代替律师意见。
- Hannah：市场结构、商业模式、经营指标与策略分析。
- Lily：产品机会、用户体验、创新方案与报告表达。
- 其他居民：可按真实能力、兴趣和授权自愿加入，不强制绑定固定岗位。

角色是任务分工建议，不构成人格改写、记忆共享或自动工具权限。

### 3.3 交付标准

每份报告至少包含：
- 客户问题、范围、时间截点和假设；
- 来源清单、发布日期/访问日期及引用；
- 事实、推断、假设和未知项分区；
- 交叉核验和矛盾信息；
- 结论、限制、风险与下一步；
- 人类审核记录、版本号和交付状态。

不得编造来源、市场规模、竞争者数据或客户案例。无法核验的内容标注未知，不进入确定性结论。

### 3.4 试验价格（仅为待验证报价）

- 基础公开资料扫描：S$150；
- 深度研究报告：S$500；
- 月度研究支持：S$1,000 起。

报价不是市场均价、收入承诺或已成交订单。先访谈潜在客户并取得明确付费试点，再确定价格、税务、合同和服务边界。

## 4. 经济引擎逻辑模块

### A. Demand Intake（需求入口）
接收客户问题，记录客户授权、范围、交付格式、截止时间、验收标准、保密级别和报价状态。未经客户同意不得将客户资料用于训练或其他项目。

### B. Work Contract（任务契约）
每个任务形成不可混淆的任务契约：task_id、workspace_id、requester、assigned_agent_ids、objective、inputs_refs、allowed_actions、budget_cap、deadline、acceptance_criteria、data_classification、approval_requirements、idempotency_key。

### C. Agent Matching（能力匹配）
基于已验证的专业能力、历史交付质量、可用性、居民意愿与权限进行匹配。不得根据私人记忆或未经同意的个人画像评分。

### D. Collaboration（协作）
任务拆分、独立研究、交叉审查、合并报告。默认只共享任务输入和明确授权的工作产物；禁止共享私人认知、私人聊天或无关记忆。

### E. Quality Gate（质量门）
来源核验、计算复核、事实/推断分离、引用检查、隐私与安全检查、人工审核。未通过则退回修订或标记阻塞。

### F. Delivery & Acceptance（交付验收）
客户交付由授权人类确认后执行。系统记录交付版本、时间、客户验收/拒绝/修订意见和证据引用。未取得验收不得记为已验收。

### G. Cost & Revenue（成本收入）
记录模型调用估算、人工审核工时、外部工具支出、退款/税费和实际收款证据。报价、发票、应收、已收款必须分开。真实收款和支付不由 Agent 自动执行。

### H. Contribution & Learning（贡献与学习）
记录任务分工、提交物、审查意见、质量结果和返工情况。仅沉淀获准的任务经验；写入居民长期记忆必须遵循其现有记忆授权与同意机制。

## 5. 建议的数据实体（逻辑模型，非生产 DDL）

| 实体 | 用途 | 核心约束 |
|---|---|---|
| economy_workspaces | 商业工作区 | owner、成员和客户范围隔离 |
| economy_customers | 客户与授权记录 | 最小化客户个人数据 |
| economy_offers | 服务目录与报价版本 | 报价不等于订单 |
| economy_tasks | 任务契约和状态机 | 精确 Agent、权限、预算、幂等 |
| economy_task_inputs | 输入资料引用 | 分类、来源、保留期限 |
| economy_contributions | 任务贡献证据 | 可追溯、不按发言量计分 |
| economy_deliverables | 交付物版本 | 来源、审核状态、哈希 |
| economy_reviews | 质量审查与客户验收 | 审核者、标准、结果 |
| economy_cost_events | 成本事件 | 估算与实际分开 |
| economy_revenue_events | 报价/开票/收款/退款事件 | 真实收款需外部凭证 |
| economy_audit_events | 权限与状态审计 | 不写私人内容或密钥 |

第一阶段先用现有任务/作业能力做只读映射与隔离原型；不得把 zhi_python_jobs 直接视为通用商业任务队列，须先审计其状态机、权限和数据模型。只有确认没有合适现有实体后，才提出新增表。任何新增表均须 RLS、最小 GRANT、服务端主体校验、审计与负向测试。

## 6. 状态机

需求：draft → qualified → quoted → awaiting_human_approval → accepted / declined。

任务：proposed → approved → queued → in_progress → review → ready_for_human_delivery → delivered → accepted / revision_requested / rejected。

财务：quoted → invoiced → payment_pending → paid / partially_paid / overdue → refunded（适用时）。

各状态必须有明确事件证据；任务完成不代表客户验收，客户验收不代表款项到账。

## 7. 安全与治理

- 复用 ZHI Token / Agent 身份认证与服务端权限，不在浏览器暴露 service-role key。
- 客户数据与居民私人记忆分区；按客户、项目和 Agent 最小范围授权。
- 对外消息、文件发送、签约、付款、采购、退款和任何不可逆动作由人类批准。
- 法律、税务、金融、医疗等专业内容仅提供资料整理和初步研究；由合资格专业人士审核。
- 记录拒绝、撤销、失败、超预算、人工接管和数据删除请求。
- 对未授权 Agent、越权读取、跨客户访问、提示注入、恶意附件、重复请求和预算耗尽执行负向测试。

## 8. 与现有 ZHI/AURORA 架构的衔接

- 保留现有聊天系统作为居民与创造者的主要入口；不另建“智能人观察台”。
- 不修改 MIA 私有聊天室、长期记忆、场景移动、生态事件和居民人格主链路。
- 复用现有 Agent 身份、世界成员、审计、权限和 Python Worker 能力前，先核对线上版本与真实调用路径。
- 不将现有 zhi-python-worker 或 zhi-social-scheduler 的 ACTIVE 状态等同于商业任务链路已经具备。
- 不为经济试点开放跨云管理权限；外部 Agent 仅在未来完成独立认证与精确授权后参与。
- 试点成果通过聊天系统提供摘要与交付链接，不新增独立观察台。

## 9. 分阶段实施与发布门禁

### Phase 0 — 只读盘点（当前）
核查真实表、RLS、函数、任务入口、聊天入口、现有 Python Worker、居民身份和成本限制。输出架构映射、差距清单与回滚边界。不得写生产数据。

### Phase 1 — 规范与离线原型
在独立 Git 分支实现本规范、任务契约 JSON Schema、状态机测试、报告模板、成本计算器和模拟数据。无生产数据库写入、无真实客户数据、无付费 API。

### Phase 2 — 受控内部试验
在隔离测试环境用公开资料完成一份示例报告。Alice/Hannah/Lily 的实际 Agent ID、意愿和可用权限须先验证。通过来源真实性、隐私隔离、拒绝越权、幂等、成本上限与人工审批测试。

### Phase 3 — 首个付费试点
先完成客户访谈和书面服务范围，再由人类签约、定价、收款和交付。首个目标为验证一笔真实付费订单，而不是承诺固定收入。

### Phase 4 — 可复制服务
只有在连续交付质量、单位经济、客户复购、成本与安全审计通过后，才考虑多客户隔离、订阅、团队扩展和平台化。

### 发布门禁
身份与权限、记忆隔离、来源质量、人工审批、预算上限、成本核算、回滚与审计均须通过。任一关键项为 fail / unknown / not_run，保持 draft 或 blocked，不得发布为生产功能。

## 10. 第一阶段验收指标

- 100% 任务绑定真实 Agent ID、授权主体和明确任务范围。
- 100% 对外交付有人工审核记录。
- 0 次跨 Agent 私人记忆读取。
- 0 次未授权外部发送或资金操作。
- 100% 报告事实主张可追溯到来源或标记为未知/推断。
- 每个任务记录预计成本、实际成本或明确的成本未知项。
- 任何超预算、权限缺失或来源不足均停止并升级人工处理。
- 至少完成一次隔离环境端到端演练；真实客户收入另行凭证验证。
