# ZHI 健康顾问接入现有智能人聊天系统：身份与部署门禁

## 当前结论

健康顾问 Edge Function v5 部署在独立 Supabase 项目 `lvxmygrgqtmzqgailmyl`（ZHIMIA）。现有 `agent-talk.html` 使用的是 Core 项目 `jozrslgdjreepxplicen`，并通过 `zhi-chat-auth` 发放共享的站点管理员访问令牌。Core 与 ZHIMIA 的 JWT 不能互换。

因此，`web/zhi-health-advisor-client.js` 不能直接插入现有页面就开始工作：它要求由 ZHIMIA Auth 签发的登录会话。不能把当前共享管理员令牌当成个人身份，也不能用它为不同用户隔离健康数据。

## 为什么不能绕过

- 健康记录属于敏感个人数据，需要稳定、可审计的个人身份。
- 现有站点密码令牌的 `sub` 是固定的 `admin`，不是实际个人用户 ID。
- 把共享令牌映射到一个数据库用户会造成所有持有该令牌的人共用同一数据身份。
- 不能关闭 JWT 校验、开放匿名读写，或把 service-role key 放进前端来“打通”接入。

## 安全接入路径

### 推荐：独立的个人登录身份

1. 为健康顾问提供 ZHIMIA Auth 的个人登录会话，或实施经审核的身份联合。
2. 明确每位用户的稳定 subject 与健康数据归属映射；映射必须由服务端验证和维护。
3. 前端只使用 publishable key，所有健康数据访问继续由 RLS 或服务端授权保护。
4. 用户明确同意后才保存聊天历史；提供撤销和删除入口。
5. 先用两个测试账号验证 A 无法读取、修改或删除 B 的数据，再开放真实用户。

### 备选：部署到现有 Core 项目

只有在 Core 项目被明确连接、完成在线 schema/RLS/函数审计，并为健康数据设计个人身份映射后，才考虑把迁移与函数部署到 Core。现有共享管理员令牌不能作为通用个人身份。不得在未审计 Core 数据库前直接运行迁移。

## 当前已完成与未完成

- 已完成：ZHIMIA 项目的健康顾问表、RLS、Edge Function v5、基础安全分流、服务端模型调用骨架、客户端适配器。
- 未完成：`OPENAI_API_KEY` 与精确 `ZHI_ALLOWED_ORIGINS` 配置；真实个人登录/身份映射；现有聊天页面接入；端到端与跨用户隔离验收。
- 当前不能宣称：健康顾问已集成到 `agent-talk.html`、普通模型问答已可用、端到端测试已通过。

## 下一步

先确认健康顾问的用户身份方案，再接入前端。最小安全方案是让每个实际使用者拥有自己的 ZHIMIA Auth 会话；如果必须沿用 Core 身份，则先连接 Core 项目并设计经过验证的身份桥接，不能直接复用共享站点访问令牌。
