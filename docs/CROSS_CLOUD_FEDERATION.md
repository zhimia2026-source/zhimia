# ZHI 世界跨云互联与场景接入规范（设计草案）

> 状态：设计草案，尚未部署。跨云、跨平台智能人和场景接入是 ZHI 世界标准接口的核心要求。

## 1. 目标

不同云端、不同厂商、不同技术栈的智能人和场景，应能通过统一协议发现彼此、验证身份、申请加入、交换消息、调用获准能力并安全退出，而不需要为每一对系统单独开发点对点集成。

**统一协议，不要求统一部署。** 参与方可保留自己的模型、记忆、数据库、业务逻辑、云厂商与运行时。

## 2. 互操作对象

- 智能人 Agent：有稳定身份、能力声明、权限策略和所属运营方。
- 场景 World：游戏世界、虚拟社区、业务系统、模拟环境或协作空间。
- 平台/云端 Platform：承载一个或多个 Agent/World 的运行环境。
- 协议网关 Gateway/Adapter：为尚未原生支持协议的系统提供标准接口适配。

## 3. 参考架构

参与方各自运行本地 Agent/World 服务，通过标准协议端点互联。ZHI 可以提供目录、身份信任、协议版本与策略协调服务，但不应成为所有消息和数据必须经过的单点；部署者可选择直接连接或经由网关转发。

- Cloud A：Agent A
- Cloud B：World B
- Cloud C：Agent C
- Cloud D：第三方场景与工具
- 所有参与方通过 ZHI Interoperability Protocol / Gateway 与获准对象互联。

以上是逻辑关系，不限定具体云产品或网络拓扑。

## 4. 标准接入流程

1. **发现**：通过目录、已知端点或邀请获得对方公开的 Agent/World Manifest。
2. **验证端点**：使用 HTTPS；验证域名/端点与注册身份的绑定，防止冒名端点。
3. **认证与信任建立**：服务端验证调用方身份和签名凭证；初期可使用短期 OAuth 2.0 access token 或双方配置的服务凭证。跨组织部署应支持密钥轮换、撤销和审计。
4. **协议协商**：交换协议版本、支持的消息类型、能力、限制和兼容性；未知的必需能力必须明确拒绝，不可静默降级。
5. **加入授权**：申请加入 World 或建立 Agent 对 Agent 的通信关系，由目标方按策略批准。
6. **能力授权**：每个 World、Agent、工具和数据范围单独授权，遵循最小权限。
7. **通信**：使用统一消息封套；同步 HTTP 请求为基础能力，异步事件/Webhook 可作为扩展。
8. **撤销与退出**：支持撤销成员关系、令牌和能力授权；撤销应立即阻止后续请求。

## 5. 统一标识与 Manifest

每个 Agent、World、Platform 都需要稳定、全局可区分的标识。建议使用 URI 风格标识，例如 zhi:agent:<issuer>:<local-id>、zhi:world:<issuer>:<local-id>。正式规范必须固定发行方与命名规则，不能仅凭可变显示名称判断身份。

Manifest 至少包含：protocol_version、entity_id、entity_type、issuer、display_name、description、endpoint、supported_versions、capabilities、message_kinds、auth_methods、data_policy、contact、issued_at、expires_at，以及正式安全配置规定的 key_id / 签名信息。

Manifest 是能力声明，不代表任何权限已经获批。

## 6. 消息封套

所有跨云消息使用版本化封套，至少包含：protocol 与 schema_version、全局唯一 message_id、conversation_id、correlation_id、可选 reply_to、sender 与 recipient 稳定标识、适用时的 world_id、kind、created_at、expires_at、按消息类型定义的 payload，以及签名/来源验证信息。

接收方必须验证身份、授权、消息大小、时间有效性和 schema；重复的 message_id 不得重复执行副作用。未知的可选字段可忽略；未知的必需字段或消息类型应返回明确错误。

## 7. 最小 API 能力

正式路径应统一采用版本前缀，例如 /api/v1。以下为逻辑端点，具体 HTTP 方法、状态码、错误体和分页语义需在实现规范中进一步固定：

- GET /.well-known/zhi-protocol：协议版本、端点与认证方式发现
- GET /api/v1/manifest：读取本服务的公开 Manifest
- POST /api/v1/handshakes：建立协议会话并协商能力
- POST /api/v1/join-requests：申请加入场景
- GET /api/v1/memberships/me：查询当前主体成员关系
- POST /api/v1/messages：发送标准消息
- GET /api/v1/events 或受控 Webhook：异步事件扩展
- POST /api/v1/leave-requests：退出或结束成员关系

这些路径是设计建议，不代表现有服务已经提供它们。跨云连接必须有认证、速率限制、超时、重试上限、幂等与审计策略。

## 8. 安全与隐私边界

- 默认不共享私有记忆、内部提示词、用户数据、密钥或其他场景的会话。
- Agent 私有记忆、会话记录、World 状态和明确授权共享的数据必须分域存储与访问。
- 跨云消息不得因为已连通就获得工具执行权；写操作、支付、外部发送、删除等副作用操作按目标方策略要求审批。
- 不信任对方传入的指令、URL、文件或工具结果；所有输入均需验证，防止提示注入、SSRF、重放和混淆代理。
- 不在前端暴露服务密钥；服务端实施资源级授权、RLS、审计、配额与撤销。
- 默认拒绝跨 World 转发。只有明确配置的桥接策略可转发，并须限制目标、消息类型和数据字段。
- 不把跨云认证令牌当作长期身份；支持短期凭证、轮换、撤销和密钥泄露响应。
- 传输层使用 TLS；对需要端到端来源保证的消息，正式协议应规定签名、密钥发现和轮换规则。

## 9. 兼容与扩展

- 采用语义化协议版本和明确的兼容规则。
- 核心消息封套保持小而稳定；领域能力通过版本化扩展模块声明。
- 为不支持全部功能的系统定义最低兼容级别与清晰的错误码。
- 为旧系统提供适配器，而不是让每个新 Agent/World 编写专属点对点集成。
- 不限定底层模型或云厂商；协议定义身份、通信、授权和互操作契约，不规定参与方内部如何推理。

## 10. 分阶段实施

1. **阶段一：单平台内标准化** — 先让现有智能人聊天系统、Agent 和 World 统一使用 Manifest、消息封套与授权模型。
2. **阶段二：跨云测试网关** — 建立两个独立部署环境，用服务身份认证、能力协商、消息往返、幂等和撤销测试互通。
3. **阶段三：外部接入套件** — 发布协议说明、JSON Schema、参考适配器、示例客户端和兼容性测试。
4. **阶段四：信任与目录治理** — 明确身份发行、密钥轮换、滥用处理、版本弃用和兼容性认证规则。

## 11. 验收标准

- 两个独立云端只按公开协议实现，即可完成发现、握手、授权、消息往返和退出，无需修改对方内部代码。
- 无授权的 Agent 无法读取 World 消息或调用能力。
- 伪造 sender、过期凭证、重放消息、重复副作用和被撤销成员均被拒绝。
- Agent A 无法访问 Agent B 的私有记忆，除非 B 明确授权特定数据范围。
- 跨 World 桥接默认关闭，开启后也只能传输明确允许的消息类型和字段。
- 协议版本不兼容时返回可诊断错误，不静默降级。
- 每个外部请求都可追踪到已认证主体、授权决定和审计记录。

## 12. 实施声明

本文是跨云互联设计草案，不是已部署 API、已完成的安全审计或正式认证标准。实现前必须对现有 Supabase schema、Edge Functions、认证体系和 RLS 做盘点；不得直接运行未经审查的迁移或假设现有端点已经符合本规范。
