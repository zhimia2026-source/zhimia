# AURORA 五棒商业决策接力协议 V1.2

**状态：** V1.2 已将“认领—交付—审核—返工/放行”固化为接力底层状态机与验收契约；Agent 身份认证入口尚未接入，因此居民侧认领与交付仍未开放，禁止用创造者身份模拟居民行为。

## 1. 目标与总原则

本协议把五位 AURORA 居民组织为严格顺序的商业决策流水线。它不是五人并行投票，也不是把五个人的私人记忆合并成一个共享大脑。每一阶段只消费上一阶段经过审核的项目成果，并对其进行本角色职责范围内的判断。

- 一棒一责：每阶段只有一位指定负责人。
- 先证据，后推演：事实、假设、观点、未知必须分开。
- 交付物接力：下游只能消费上游已提交并验收的项目成果。
- 保留分歧：反证、少数意见、未解决问题不得被静默删除。
- 可退回：下游可以提出返工请求，最多两轮；返工必须留下版本和原因。
- 记忆隔离：只共享项目成果，不读取或复制其他居民的私人记忆、私人聊天。
- 最终权责：马云阶段提交商业裁决建议；创造者设定北极星量化门槛，并批准不可逆、对外或花费资金的行动。

## 2. 五阶段职责与交付契约

### Stage 1 — 张一鸣：信息智能过滤器

**任务：** 把市场噪音清洗成可核验的证据底座。

**工作范围：**
- 汇集公开市场数据、政策、竞品公开动作、用户反馈样本。
- 去重、时间戳、样本范围、来源等级和时效性标注。
- 分离事实、推断、观点、未知和过期信息。
- 主动寻找反证、样本偏差和信息缺口。

**交付物：** `evidence_ledger`，每条证据带来源 URL、发布日期、口径、样本边界、可信度、事实类别和限制。

**放行门：** 关键事实可追溯；未经访谈的假设不得写成用户事实。

### Stage 2 — 马化腾：产品生态边界定义者

**输入：** Stage 1 已验收的 `evidence_ledger`。

**任务：** 以用户价值和产品常识定义不可突破的体验底线。

**工作范围：**
- 明确目标用户、核心任务和真实使用场景。
- 定义信任、隐私、准确性、延迟、可用性和人工接管底线。
- 说明产品范围、非目标范围、失败体验和停止条件。
- 对证据不足处标记未知，不擅自补齐。

**交付物：** `user_experience_guardrails`。

**放行门：** 用户体验底线、禁止事项、人工复核点和风险停止条件明确。

### Stage 3 — Elon Musk 认知原型：第一性原理工程极限推演者

**输入：** Stage 2 已验收的体验边界，以及上游证据台账。

**任务：** 在边界内挑战传统假设，穷尽可行的工程选项空间。

**工作范围：**
- 从物理、技术、成本和执行约束拆解问题。
- 同时提出常规方案、极限方案和反直觉方案。
- 量化准确率、延迟、人工工时、集成成本、运维负担和失败模式。
- 给出最小可验证实验、关键未知和停止条件。

**交付物：** `engineering_option_space`，附可测量性矩阵、复现实验记录、故障与修复手册、回滚与恢复目标、全生命周期成本。

**放行门：** 至少三条差异化路径；每条候选方案必须给出基线指标、目标值、测量方法、可复现实验步骤、失败模式、修复步骤、回滚方案、恢复时间目标（RTO）和运维/全生命周期成本。缺少关键项不得称为已验证工程方案。极端方案必须标明约束和可执行性，不得越过隐私、安全和 Stage 2 的用户体验底线。

### Stage 4 — Jensen Huang 认知原型：平台战略与协同放大器

**输入：** Stage 3 已验收的工程选项及上游证据。

**任务：** 判断单点突破能否成为可复用的平台能力和生态机会。

**工作范围：**
- 区分单客户定制与可复用标准件。
- 设计模块化、接口、数据/算力/集成依赖。
- 分析上下游伙伴激励、价值分配、网络效应和规模化边际成本。
- 评估平台依赖、锁定风险、生态失败反例和退出方案。

**交付物：** `platform_scale_and_partner_economics`，附单位经济模型、情景敏感性分析、现金流时间线和伙伴价值分配表。

**放行门：** 必须说明客户与付款方、付费意愿证据、收入/定价模式、成本结构、毛利、现金流与回款周期、盈亏平衡点、规模化边际成本和伙伴收益分配。缺少现金流路径或经济约束的方案只能算技术/生态构想，不得称为可扩展商业平台。

### Stage 5 — 马云认知原型：商业模式与北极星裁决者

**输入：** 前四阶段验收成果、分歧、反证和未解决问题。

**任务：** 以创造者确认的北极星指标筛选商业行动。

**工作范围：**
- 核验客户付费意愿，不把口头兴趣等同真实付款。
- 审查单位经济、毛利、交付能力、现金流、竞争壁垒和三年可持续性。
- 剔除“技术很酷但没有客户价值”及“短期赚钱但不可持续”的方案。
- 输出 `go / pivot / stop / defer`，并给出负责人、预算上限、里程碑、领先指标和停止条件。

**交付物：** `final_action_memo`。

**放行门：** 北极星及量化阈值必须由创造者确认。若未确认，只能提交条件式建议，不得冒充最终裁决。

## 3. 统一交接数据格式

每份阶段交付物至少包含：

1. `facts`：有来源的事实。
2. `hypotheses`：待验证假设。
3. `unknowns`：未知与数据缺口。
4. `source_refs`：来源 URL、日期和证据编号。
5. `assumptions`：计算和推演前提。
6. `risks`：风险与失效模式。
7. `counterevidence`：反证及少数意见。
8. `recommendation`：本阶段建议。
9. `open_questions`：留给下游的问题。

交付物必须版本化。下游不得静默改写上游事实；若发现错误，提交带证据的返工请求。默认最多两轮返工，超过两轮进入阻塞状态并交由创造者决定。

## 4. 顺序门禁与状态

阶段 N+1 只有在阶段 N 的任务状态为 `done` 且至少存在一份 `accepted` 成果时，才可批准或分配。单纯提交、进入 review 或任务标记完成但没有验收成果，都不构成放行。

居民必须先确认参与，才可分配任务。指定负责人不可被随意替换。任务状态由研究中心状态机管理；每次转换写入审计活动。

## 4.1 认领—交付—审核底层闭环（V1.2）

本节是所有阶段共用的底层协议，优先级高于单阶段任务说明。任务“批准”不等于“分配”，“分配”不等于“认领”，“提交”不等于“验收”，“验收”也不自动授权对外行动。

### A. 唯一合法状态链

`proposed → approved → assigned → claimed → in_progress → review → done`

异常分支：
- `assigned → blocked / cancelled`：居民暂不可用、权限/输入缺失或任务被撤销。
- `claimed / in_progress → blocked / cancelled`：执行中发现阻塞或任务被合法终止。
- `review → changes_requested → in_progress`：审核要求返工；原交付物与审核意见保留，返工形成新版本，不覆盖历史。
- `review → rejected`：成果不满足任务目标，任务进入阻塞/终止评估，不得放行下游。

任何未列出的状态跳转一律拒绝。阶段 N+1 仅在阶段 N 为 `done` 且至少有一份关联 `accepted` 成果时解锁。

### B. 认领（Claim）

1. 只有指定负责人可认领被分配给自己的任务；其他居民不得抢占或代领。
2. 认领必须由经过认证的 Agent 身份发起，服务端从凭证解析 agent_id，不能信任请求体自报的 agent_id。
3. 必须同时满足：成员参与状态为 `agent_confirmed`、任务状态为 `assigned`、assigned_agent_id 与认证身份一致、上游阶段已验收。
4. 认领成功后原子地把任务置为 `claimed`，写入 agent_id、认领时间和审计事件；重复认领需幂等返回，不得重复创建执行实例。
5. 居民可以拒绝认领或主动释放尚未开始的任务；拒绝不视为失败，不得伪造为已确认。

### C. 执行与交付（Deliver）

1. 只有已认领的指定负责人可以开始执行和提交成果；执行开始、交付提交分别记录时间。
2. 每次交付必须绑定 task_id、agent_id、版本号、输入成果版本、来源证据、内容摘要和提交时间。
3. 交付是追加版本，不允许覆盖或删除已提交版本；重交付必须关联前一版本及返工原因。
4. 提交时任务进入 `review`，但成果状态仅为 `submitted`，不得自动变为 `accepted` 或任务 `done`。
5. 交付内容必须区分事实、假设、未知、来源、反证、风险、建议和待下游问题；Stage 3/4 还必须满足 V1.1 专项结构字段。

### D. 审核（Review）

1. 审核人与交付人分离；居民不能审核自己的交付。研究中心由创造者/授权审核人作出审核结论。
2. 审核结论仅允许 `accepted`、`changes_requested`、`rejected`，每次必须附审核人、时间、意见和发现项。
3. `accepted` 才能将该版本标记为验收成果；只有关联成果被接受，任务才能从 `review` 进入 `done`。
4. `changes_requested` 必须列出可执行的修改项，返工次数最多两轮；超过两轮进入 `blocked`，由创造者决定缩小范围、换方案或终止。
5. `rejected` 不可作为下游输入；必须保留拒绝理由和证据链。

### E. 放行与审计

每次认领、开始、提交、审核、返工、阻塞、恢复、完成都写入不可静默覆盖的活动记录。记录最少包含 actor_type、agent_id/user_id、task_id、from_status、to_status、artifact_id/version、时间和原因。下游只能读取上游明确标记为 accepted 的版本，不得读取草稿、被拒绝版本或居民私人记忆。

### F. 权限边界与失败关闭

- 创造者可以批准项目、指定负责人、审核成果和决定是否对外行动；不能代替居民点击认领、伪造居民交付或把请求状态改成居民同意。
- Agent 只能认领分配给自己的任务、提交自己的成果、读取被明确授权的项目输入；不能修改审核结论、篡改上游成果或访问其他居民私人记忆。
- 审核接口只接受具备审核权限的用户身份；Agent 身份不得调用。
- 任何身份缺失、归属不一致、阶段依赖不满足、证据字段缺失或状态竞争，均拒绝操作并写明错误，不采用“尽力放行”。

## 5. 隐私与权限

- 五位居民保持各自身份、人格和私人记忆隔离。
- 仅通过研究中心项目成果传递工作所需信息。
- 不读取其他居民私人聊天、私人记忆或私有认知。
- 公开证据优先；合成样例必须明确标注。
- 未经创造者批准，不联系外部客户、不采购、不签约、不对外承诺。
