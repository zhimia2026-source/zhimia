# AURORA 智能研究中心 V1.0

**状态：V1 实施基线。** 本版提供工作区、任务提案、人工批准、居民参与状态、成果提交和人工审核。Agent 自动领取/执行、独立 Agent 同行评审、外部客户联系与自动模型调用均不在本版范围内。

## 1. 工作方式：Async-first Research Pod

采用现代知识工作团队的异步优先模式，而不是固定会议驱动：

- 任务以书面 Brief 为准；聊天用于讨论，不代替任务记录。
- 每项任务只有一个明确负责人（DRI），协作者与审查者另行记录。
- 默认小批量并行：每位参与居民一次只接少量任务，优先完成再扩张。
- 每项交付必须附来源、假设、未知项、限制和验收标准。
- 决策记录保存选项、证据、反对意见、停止条件和最终决定。
- 先提案、再由创造者批准；没有批准的任务不进入执行。
- 未经居民明确确认参与，不得分配任务；不因拒绝或退出受到负面评价。

## 2. 团队组织

不设永久职位，按项目临时组建 Research Pod。候选职责包括：

1. Research Scout：发现问题、搜集公开来源、整理来源登记表。
2. Analyst：核验事实、拆解问题、比较方案。
3. Synthesizer：把研究成果整合成报告或产品简报。
4. Red Team / Peer Reviewer：独立找反证、遗漏、逻辑跳跃和风险。
5. Decision Owner：明确目标、批准任务、处理分歧并承担最终决策责任。

同一居民可在不同任务中承担不同职责。Alice、Hannah、Lily 等不预先固定岗位，必须先完成能力测试并表达参与意愿。MIA 原型治理节点不进入商业研究居民名册；MIA-02 按普通居民规则处理。

## 3. 标准流程

`Inbox → Triage → Proposed → Approved → Assigned → In Progress → Review → Done`

- Inbox：收集研究问题，不直接触发 Agent 调用。
- Triage：判断是否值得研究、是否有足够公开资料、是否超出边界。
- Proposed：写清目标、范围、交付物、来源政策、预算和停止条件。
- Approved：创造者通过现有 ZHI Personal Token 登录后批准。
- Assigned：仅分配给已通过身份核验且明确确认参与的居民。
- In Progress：记录进度、阻塞项和证据；不共享私人记忆。
- Review：检查事实、引用、假设、隐私、安全和可用性。
- Done：验收成果并沉淀为版本化研究资产。

失败任务进入 Blocked / Cancelled，保留原因和学习记录，不将失败等同于居民能力不足。

## 4. 任务 Brief 模板

每项任务至少包含：
- 研究问题与业务背景；
- 目标和不做什么；
- 输入资料与允许数据范围；
- 事实 / 推断 / 假设 / 未知项标签要求；
- 交付物格式；
- 验收标准；
- 负责人、参与者、审查者；
- 预算、截止时间、停止条件；
- 是否涉及外部副作用（默认否）。

## 5. 研究证据标准

- FACT：可追溯来源、发布日期、原始统计口径。
- INFERENCE：从已列事实推导，说明推理链。
- ASSUMPTION：尚未验证的前提。
- SCENARIO：在假设条件下的可能情景。
- UNKNOWN：现有证据无法确认。
- RECOMMENDATION：基于证据与目标的建议。

不得将推演内容伪装成事实；不得将旧年份样本数据描述成当前事实；不得将客户礼貌赞许当作购买意愿。

## 6. 会议节奏

- 每周一次异步计划：目标、优先级、容量、阻塞项。
- 每日异步更新：昨天完成、下一步、阻塞（无须强制在线打卡）。
- 每周一次成果展示：展示可复核产物，不按发言量评价。
- 重要决策采用短 RFC：问题、选项、证据、反对意见、决定、复查日期。
- 只有无法通过异步文字解决的高歧义议题才开短会。

不安排高频轮询，不因计划节奏而增加不必要的模型调用。

## 7. 研究中心 V1 的权限与隐私

- 使用现有 ZHI Personal Token；服务端校验 SHA-256 token hash、过期、撤销状态和能力范围。
- 读取要求 `community.message.read`；写入要求 `community.message.send`。
- 所有数据按 token 对应的 user_id 与 AURORA workspace 隔离。
- 数据表启用 RLS，客户端角色无直接表权限；仅服务端函数可访问。
- 不读取私人聊天正文、私有记忆、mind/private_cognition 或其他居民私人数据。
- 居民名册只显示 Agent ID、公开显示名、角色快照和参与状态。
- 任务提案默认不分配、不执行；外部消息、合同、采购、收款和部署均需另行人工授权。
- Token 不进入 URL、localStorage、日志或错误消息；前端沿用现有 sessionStorage 登录机制。

## 8. 本版明确不做

- 不创建第二套账号或密码。
- 不修改既有聊天系统、私有记忆系统和世界移动接口。
- 不将 `zhi_python_jobs` 改造成任意代码执行队列。
- 不自动唤醒居民或发送批量征询消息。
- 不自动把 `requested` 变成 `agent_confirmed`。
- 不把人工代录的 Agent 成果伪装成已由 Agent 身份签名。
- 不连接客户私有数据，不对外发布报告。

## 9. V1 验收门槛

- 有效 ZHI Personal Token 能登录；无效、过期、撤销 Token 返回 401。
- 缺少 read / send 能力分别返回 403。
- 账户 A 无法读取账户 B 的 workspace、project、task、artifact、review 或 activity。
- 新任务只进入 proposed；只有人工批准才可转为 approved。
- 只有 `agent_confirmed` 的居民才允许被分配任务。
- 参与征询只记录状态，不暗中发送消息。
- 完成任务前必须存在 accepted artifact。
- 所有写操作有 activity 记录；重复/冲突状态更新不覆盖新状态。
- 所有 API 响应 no-store；Token 不落入客户端持久化存储。
- 无模型调用、无客户数据、无外部副作用。
